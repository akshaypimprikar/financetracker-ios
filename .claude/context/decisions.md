## 2026-08-01 — Backward Compatibility: Lower Deployment Target — Rejected at Spec Stage
No plan or code followed; rejected during `/spec` exploration before a spec document was written.
**Approaches considered:** (1) refactor `CategorySuggesting.swift` so the protocol has zero `FoundationModels` imports — move `@Generable`/`@Guide` types into `FoundationModelsCategorySuggester.swift` only, protocol returns a plain `Sendable` DTO — then `@available(iOS 26, *)`-gate the concrete suggester and its construction in `BudgetViewModel`/`ImportViewModel`, folded into the same spec as the deployment-target change; (2) split the `CategorySuggesting` protocol refactor into a prerequisite sub-spec, with the deployment-target/CI spec blocked on it; (3) keep `IPHONEOS_DEPLOYMENT_TARGET` at 26.4 for now, revisit lowering it only if/when the `CategorySuggesting` protocol gets refactored for unrelated reasons.
**Chosen:** (3) — keep the deployment target at iOS 26.4.
**Reason:** Initial investigation (grep for `@available`, common iOS-26-only SwiftUI modifiers) found no technical barrier to iOS 18, but missed that `CategorySuggesting.swift` — the domain service *protocol* file itself, not just the concrete `FoundationModelsCategorySuggester` — imports `FoundationModels` and returns a `@Generable`-typed `CategorySuggestionResult`. Apple confirms `FoundationModels` requires iOS 26.0+ at build time (linker won't resolve symbols below that), so the protocol boundary is availability-locked to iOS 26+, and both consuming ViewModels reference it unconditionally via a default-parameter `FoundationModelsCategorySuggester()`. Properly gating this is a real protocol refactor (decoupling the DTO from `@Generable`, adding `@available` at the construction sites), not a one-line deployment-target edit — not worth doing as a standalone effort right now. If `CategorySuggesting` gets refactored later for other reasons, revisit iOS 18 as the floor then; iOS 17 remains the hard SwiftData floor if it's ever revisited. iOS 26 adoption was ~84.5% as of June 2026 (telemetrydeck.com), so the cost of staying at 26.4 is currently low.

## 2026-07-15 — CSV Import Async Migration
**Approaches considered:** (1) plain sequential cancellable `Task`, no `TaskGroup`; (2) `TaskGroup` with actor-serialized chunk children (writes still serialize on the single `@ModelActor`, cancellation propagates automatically to unstarted chunks); (3) fully pipelined `TaskGroup` where each child also parses/hashes its own chunk concurrently, overlapping CPU work with the actor's in-flight save.
**Chosen:** (2) — `TaskGroup` with actor-serialized children, plus fixing the previously-unscoped O(N×M) `existsWithHash` dedup scan in the same PR, plus a real percentage progress bar computed from the `TaskGroup`'s completion stream (no separate `AsyncStream` type needed).
**Reason:** Satisfies the audited bug (main-thread blocking on both the dedup scan and the per-row save) and the backlog's literal "TaskGroup" requirement without the added concurrent-parsing complexity of full pipelining, which doesn't fix a documented problem and was deferred as a Future Extension Point instead.

## 2026-07-19 — Foundation Models Spike: CSV Payee→Category Suggestion
**Approaches considered:** (1) `ImportViewModel`-orchestrated enrichment via a new `CategorySuggesting` domain-service protocol + `FoundationModelsCategorySuggester` adapter, with accepted suggestions persisted onto `Transaction.category` through a new mutable `ParsedTransaction.categoryID` field consumed by `TransactionImportActor.save`; (2) same suggestion pipeline but read-only display, no persistence changes to the import/save path; (3) a separate post-import categorization review screen operating on already-persisted transactions, with zero changes to the CSV parse/save pipeline.

## 2026-07-26 — Category Seeding & AI-Suggested Category Creation
**Approaches considered:** (1) extend `CategorySuggestion` (the `@Generable` struct) directly with a plain `matchedCategoryID: UUID?` field; (2) wrap it in a new `CategorySuggestionResult` domain type, leaving `CategorySuggestion` as pure model output; (3) drop match-tracking entirely and have the View re-derive existing-vs-new by comparing the suggestion's name against its own category list at render/tap time.
**Chosen:** (2) — `CategorySuggestionResult` wrapper.
**Reason:** Mixing a post-hoc-computed field into an `@Generable` struct's stored properties is unverified against the real macro's schema-synthesis behavior — safer to keep `CategorySuggestion` as pure `@Guide`-annotated model output. The suggester already computes the match once internally (previously discarding it by returning `nil` on a miss); wrapping preserves a single source of truth for that determination rather than having the View re-derive it, matching the same DTO-boundary judgment already applied for `CategoryCandidate` earlier in this feature. Also folds in: one-tap AI-suggested category creation with fixed `.expense` type and default icon/color, a Menu-row sparkle highlight for the matched suggestion, and refreshing `ImportViewModel`'s categories/accounts on every `ImportSheet` appearance to fix the stale-list bug found during PR #62's manual verification.

## 2026-07-28 — Category Seeding & AI-Suggested Category Creation: Seeding Reversed
Reverses the seed-category-taxonomy decision from the 2026-07-26 entry above, before `/plan` — no code was written against it.
**Approaches considered:** (1) keep the 11-category seed list as originally specced; (2) drop seeding entirely, let category population emerge from AI-suggested creation (or manual add), with device-capability-aware empty-state guidance where a screen is actually blocked by zero categories.
**Chosen:** (2) — no seeding.
**Reason:** A full app-wide audit of `Category` usage found only one screen (`AddBudgetSheet`) is genuinely blocked by an empty category list — `AddTransactionSheet` already has a working `"Uncategorized"` fallback and was never actually blocked, correcting an assumption made earlier in this same spec's discussion. With only one real blocked screen, a blanket pre-populated taxonomy became harder to justify than targeted empty-state handling: on an Apple Intelligence-eligible device, `AddBudgetSheet`'s empty state points at CSV import only, making AI-driven creation the actual mechanism by which categories come to exist rather than an addon patching a cold-start problem seeding would have papered over; on an ineligible device, it falls back to the existing manual "Add Category" flow so that hardware isn't regressed. Surfaces two new requirements not present in the seeded version: `createAndAssignCategory` must dedupe against an existing category by name before creating (previously a rare edge case, now the routine first-import case with no baseline to match against), and a cheap rematch pass must keep other pending suggestions' matched state accurate after each create, since suggestions for a whole CSV are computed in one batch before any user interaction.

## 2026-08-18 — UI Appeal Pass
Follow-on to the separately-specced `Theme.Glass` token addition (PR #95, no spec doc — small enough to scope directly in `/design`'s own token-proposal flow). This spec covers the views that consume those tokens plus four independent fixes found in the same HIG-alignment review.
**Approaches considered:** For the Dashboard category chart specifically: (1) inline group-and-sum aggregation in `DashboardViewModel.load()`, matching the existing `spendingThisMonth` precedent; (2) a new Domain Service method for category-spend aggregation. For chart bar coloring: (a) uniform `Theme.Charts.spendingBar`, matching `BudgetDetailView`'s existing single-hue convention; (b) per-category `Color(hex:)` bars. For progress-bar category coloring scope: Dashboard-only vs. app-wide (Dashboard + BudgetListView + BudgetDetailView).
**Chosen:** (1) inline aggregation, (a) uniform chart bar color, app-wide progress-bar coloring.
**Reason:** A category-spend group-and-sum isn't complex enough to justify a new service given the existing inline-aggregation precedent already in the same ViewModel method. Per-category chart bars would create a second, conflicting visual convention for "spending" charts against `BudgetDetailView`'s already-shipped single-hue bar chart — uniform color keeps one convention app-wide, while category color is instead expressed through the progress-bar tint (a different visual channel) to avoid overloading two components with the same signal. App-wide progress-bar scope confirmed directly by the user over Dashboard-only, on the reasoning that partial rollout would leave the Budgets tab visually inconsistent with the screen that prompted the change.
